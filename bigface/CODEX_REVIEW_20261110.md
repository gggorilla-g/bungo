## 1. 効果の大きい改善（優先順）

1. **主光と環境光の比率／色調**
   - 画像：顔・壁・床が似た黄褐色の明度にまとまり、落ち影だけが硬く目立つ。形の単純さより光の整理が優先。
   - 元bf.js 271–278行 ep01：hemisphere 1.15→0.65、地面側を暖色から低彩度の寒色0xBEC9C5へ。sun 1.6→1.25。毎フレーム／室内カメラのhemi上書きも合わせて修正。
   - 元11行grad：[175,225,255]→[145,210,255]。環境光を減らした上で3段の読み分けを試す。NoToneMapping/SRGBは維持。ACESを足すだけではパレットが変わり、照明の問題は直らない。
   - コピー実装済み。明るさの値は実写測定値ではなくA/B用初期値。室内PointLightは現状維持、顔の白飛びを確認して次に調整。
2. **接地影＋影領域の管理**
   - 元275行のPCFSoftShadowMapではradius=6を大きくしても面光源の柔らかい影にならない。コピーはwindow.setupのPCFShadowMap＋radius=2へ。これはフィルターによる軟化で、距離に応じた半影ではない。
   - ep01のshadow cameraを横±7に絞り、sunとtargetを正面0／裏口40／アイキャッチ−60に同時移動。元コードの固定影領域では裏口が主な影範囲から外れる。mapSizeは2048を維持し、bias/normalBiasを縮小（−0.00015/0.015）。ニキビ状の影や影離れは原寸確認が必要。
   - bfの足下にCanvas製の薄い放射グラデーションPlaneを追加。狭い接地補助であり、全面AOの代用ではない。室内床上面0.05に対して高さ0.058、屋外は0.012。足裏が接地していないこと自体は別途直す。
   - コピー実装済み。真の面光源をThreeのToonでそのまま使う案は採らない。必要なら次段階で複数方向の影付き光の平均化を試すが、SwiftShaderでは費用増が大きい。
3. **輪郭線を画面幅で揃える**
   - 元14–19行mesh：形状を一律倍率で拡大するため、長い柱・窓枠・小さい手足で線幅が変わる。
   - コピーoutlineMaterial/mesh：BackSideは維持し、onBeforeCompileでproject_vertexの後に投影面上の法線方向へ0.7/1.15px押し出す。normalMatrixで非等方スケールを考慮。色はPAL.ink、輪郭は影を落とさない。
   - 実装済み。ただし箱の角の割れ、交差部、遠景の線、GLSLコンパイルは未検証。頂点の硬い法線では完全なシルエット抽出ではない。試写で割れが出た箱は線を外すか、面取りした専用輪郭メッシュにする。解像度を変えた場合もピクセル幅固定なので縮小比較時に注意。
4. **材質は大きな模様より微細な差**
   - 元49行bigFaceのclothにgrain(PAL.cloth,128,128,3)を追加。顔は無地のまま。木・石・壁の既存grainは再利用し、ノイズや反射を一律追加しない。
   - ToonにはStandardのroughnessによる素材分離はない。服・紙・木は色差・模様の方向・エッジ形状で分ける。元からToonなので「光沢を消す」だけでは改善しない。
   - 服だけコピー実装済み。床の大きなタイル線は現状でも視線を奪うので、次回は線のalpha 0.16→0.08程度の比較を推奨。全面的な色加工は不要。

## 2. モーション（04）

- **頭の遅れ**：元327行以降は速度の絶対値から加速度を計算。移動方向や後退を区別できず、旋回の遅れもない。大きな場所移動の瞬間だけvを0にしても、その次のサンプルで偽の加速度が出る。初回timesが途中だと履歴なしで始まり、逆順時刻にも対応しない。
  - コピー：1/120秒の固定刻み、初回は0から積分、逆方向評価時は再計算。場所移動では頭・速度をリセット。2.3Hz/減衰比0.3→2.0Hz/0.58とし、停止後の長いビヨビヨ感を抑える。
  - 残り：最終的には速度ベクトル差をキャラのローカル前後・左右へ投影しpitch/rollを分ける。現在の修正は方向別のばねまで実装していない。仕様の遅れ0.08〜0.16秒は周波数だけで保証できず、体停止から頭の最大傾斜までをフレームで測る。
- **歩き**：元walkPoseはonがfalseになる瞬間に脚・腕・上下動をゼロへ戻す。元のphaseは速度と無関係な一定周期で、ease移動中に滑る。足音も独立した秒数指定。
  - コピー：主人公のphaseを移動距離に連動（一歩0.48仮値）、歩行ウェイトを時定数0.065秒で減衰、上下動をabs(cos)から滑らかな2倍周期へ。
  - 残り：これだけで足滑りは解消しない。短い脚に対して道のりが速い。特に裏口へ5.55単位/2.4秒、最大約3.47単位/秒。軸から足まで約0.3に振幅0.55radでは一歩0.48も長め。移動距離・尺を先に直し、支持足のワールド座標を固定、遊脚だけ弧を描かせ、2関節IKまたは脚Groupの位置補正を追加する。一般人・子どもの一定周期は未変更。
- **衝突**：元bumpは接触時にsq=0.055へ即ジャンプし、0.04秒の加算が切れる点も不連続。コピーはゼロから立ち上がる減衰sinへ。setFaceは前後圧縮depth、横縦=1/sqrt(depth)で体積保存し目口も追従。
  - 残り：最大圧縮は式の係数5.5%より小さく、実測調整が必要。扉の面と顔表面から接触位置を決め、頭停止→2コマ程度遅れて胴体を止める。ep01Testには胴体の遅れがあるが、本編ep01には同等の処理がない。アイキャッチの着地式も別実装で未修正。
- **止まった後**：減衰は今回調整。小さい振幅・速度になったらゼロへ吸着させる処理、支持足の収まり、後退時の頭の符号が次の課題。常時のsin揺れを追加しない。
- **再現性**：st.happyの毎フレーム初期化も追加。主人公ばねのseekは改善したが、bf2.body.scale等は逆seekで状態が残り得る。全体を任意時刻純関数にしたわけではない。カットごと新規setupが確実。

## 4. Three継続かBlenderか

- **今はThree継続を推奨**。見えている課題の大半は演技、接地、遮蔽、照明設計。レンダラーだけ替えても残る。まず修正の静止画A/B→短い動画→全尺の順に判断。
- SwiftShader用：低解像度540×960プレビュー、本番1080×1920。まず影2048・光源1個を維持。多光源シャドウや全面SSAOは計測後。速度の実測値はこの環境ではない。
- Blenderを試すなら**3ショットだけ**：外観MS／室内顔CU／窓の二人。Eeveeで大きなArea light、接触部の遮蔽、適切なサンプル、面取りを評価。トゥーン材質や影の仕様はインストール版で確認する。CyclesはShader-to-RGB依存のEevee材質をそのまま使えないので別設計が必要。
- 効果が出る移行範囲：モデル・法線・UV・材質・カメラ・アニメーションのベイクまで。Threeで絵を完成させて動画だけBlenderへ入れても影や接地は改善しない。脚本、イベントJSON、音楽・SE・FFmpeg仕上げは既存を残せる。
- 工数目安（実測ではなく、既存実装を理解した担当者1名）：Threeの見た目調整0.5〜1.5日、足固定とモーション整理1〜3日。Blender比較用3ショット2〜4日、全話用の再利用リグ・本編移植5〜10日程度。データ変換・カメラ一致・音同期検証を含め、レンダリング待ちと修正回数は別。GPUなしでのEevee可否・Cyclesの速度は現地ベンチマーク必須で、移行による高速化は保証しない。
